# Learning Record 0005：删掉和换个地方放，是两种操作

## 日期

2026-08-13

## 上下文

第 0005 课「结果预算」。在 `mini-cc/src/v4/` 加入 `budget.ts`，两层闸分别接到 `runTools.ts`（结果产生处）和 `loop.ts`（请求发出前），对照 `src/utils/toolResultStorage.ts`（1041 行）与 `src/constants/toolLimits.ts`。

## Insight

### 一、裁剪上下文时，「删」和「搬」的性质完全不同

截断改变的是**信息量**，落盘改变的是**寻址方式**。

落盘之后全文一直在磁盘上，模型拿着路径可以自己 `read_file` 取回来。日常省下的是「可能不需要的完整信息」，真需要时一次读取补回来。截断做不到这件事，被截掉的部分从系统里彻底消失了。

代价是三样，都要提前想清楚：

1. 要写磁盘，于是有失败路径。**源码在落盘失败时原样返回全文**，因为 `tool_use` 必须有配对的 `tool_result`，这条 API 硬约束比省钱重要。
2. 模型可能真的去读，多花一轮。所以预览要够大（2KB）、挑选要克制（够用就停）。
3. 落盘决定必须跨轮次稳定，多出两个状态字段和 resume / 子 agent / fork 三种继承情况。

### 二、一层预算不够，因为「合规」是可以叠加的

单个结果的阈值和每消息的聚合预算管的是两件事。10 个并行工具各吐 40K，**每一个都合规**，但它们在 wire 上是同一条 user 消息，加起来 400K。

这一条直接接上第 0003 课：并行工具的结果被收集成一条消息追加到历史。分批算法制造了并行，预算的第二层来收拾并行的账。

真实源码在这里比 mini-cc 麻烦得多：`normalizeMessagesForAPI` 会把连续的 user 消息合并，只有 assistant 消息才制造边界，所以预算的分组函数必须用同样规则再走一遍（`toolResultStorage.ts:600`）。分错了不会报错，只会在**最该生效的时候悄悄失效**。

### 三、「见过就不能改」这条规矩，理由不在这个结果本身

这是本课最反直觉、也最值钱的一段。

预算每轮都跑，而每轮都发完整历史。同一个老结果被反复看到。如果这次的判断和上次不一样（上轮发全文、这轮发预览），请求前缀就从那一处断了，往后的缓存全部作废。

所以：进了 `seenIds` 命运就定型。三类处理：

| 分类 | 上轮决定 | 这轮 |
|---|---|---|
| `mustReapply` | 替换过 | 原样贴回，纯 Map 查表，零 IO，逐字节相同，不可能失败 |
| `frozen` | 见过没替 | 从此不许替，就算现在超预算 |
| `fresh` | 没见过 | 唯一能动的 |

**提炼：一个局部最优的决定（现在替换能省额度），在跨轮次的系统里可能是负收益。判断边界要放到「整条时间线」上，不是单次调用上。**

`replacements` 存的是**字符串本身**而不是「稍后重新生成」，理由同源：改一下预览模板或体积格式，重新生成的字符串就和当初发出去的差一点，差一个字符前缀就断。

### 四、豁免必须配自限

`FileReadTool` 声明 `Infinity`，两层预算都豁免它。理由是循环：Read 的结果落盘后，模型要拿全文只能再 Read 那个文件，那次又超阈值又落盘。

但豁免不是免费的。源码注释交代了对价：*the tool already self-bounds via its own limits* —— Read 自己带行数上限和 `maxTokens`。

`mini-cc` 的 `read_file` 什么边界都没有，所以第 2 轮那次取回全文原样进了历史，一轮没少。**这是课程里留的一个真实漏洞**，练习是给它加 `offset` / `limit`。

另外注意 `Infinity` 判断的**位置**：它在 `Math.min` 之前返回，而且源码特意写了 *Checked before the GB override so tengu_satin_quoll can't force it back on*。又一次「位置即语义」，和第 0004 课同一个母题。

### 五、`inc-4586`：一行代码，全部生命保障在注释里

空的 `tool_result` 落在提示词末尾时，某些模型会把 `</function_results>` 后的两个换行误当成轮次边界，直接收工零输出。而空输出完全合法（静默成功的 shell 命令）。

补丁是塞一句 `(${toolName} completed with no output)` 进去。

**删掉它测试全绿。** 几个月后又会有人删掉它。那段带事故编号的注释是它唯一的保护。这类代码在任何长期维护的系统里都存在，值得单独识别出来。

## 已实测验证的事实

- `--thresholds`：`read_file` = ∞，`run_tests` 声明 30,000 生效，其余被 50,000 夹住
- `--budget`：1200 行日志 44.4KB → 2.1KB 落盘；400 行 14.7KB 原样通过
- `--aggregate`：8 × 28.4KB = 232,256 超 200,000 预算，替换 2 个后降到 178,548
- `--stability`：带状态时四轮 hash 恒为 `505d1eb29a`（第 3 轮改预算也不动）；不带状态时第 3 轮变成 `fca65578d2`，前缀断裂
- 完整 agent 跑通：三个 run_tests 并行 → 两个落盘 → 模型第 2 轮自己 `read_file` 取回全文

## 引申

- **「量出来」比「讲出来」有效。** `--stability` 用 sha1 指纹把「前缀稳定」这个抽象概念变成了一列可以直接对比的十六进制。这个手法可以复用到第 0006 课（缓存命中率）和第 0007 课（压缩前后的 token 数）。
- 第 0006 课的接口已经铺好：这一课所有的「决定不能改」都以缓存为理由，下一课去看缓存本身。DeepSeek 自动缓存 vs Claude 手动断点的对照仍按 NOTES.md 的计划走。
- 报告第 06 章讲完整的上下文管理，结果预算只是第一环，后面是三级压缩（0007）和 Attachment 回灌（0008）。已在本课推荐资料里提示先扫全章。
