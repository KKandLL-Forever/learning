循环与状态

Agentic Loopagent loop00
整个系统的骨架：发请求 → 模型回复 → 回复里有 tool_use 吗 → 有就本地执行、把结果塞回对话、再发一次 → 没有就结束。一次用户提问可能触发 8 次 API 调用。 src/query.ts
query()AsyncGenerator01
核心循环函数，类型是 AsyncGenerator<StreamEvent | Message, Terminal>。它不返回答案——答案通过 yield 逐条交付；return 值是终止原因。 src/query.ts:238 · queryLoop()
Terminal终止原因01
循环的返回值：正常结束 / 用户中断 / 达到轮次上限 / 被 stop hook 拒绝。调用方靠它决定下一步控制流。 src/query/transitions.ts（源码仓库中是 stub）
State显式循环状态01
跨轮次携带的 10 个变量打包成的对象。循环里有 7 处 continue，每处都整体重写 state = { ... }——要么全写，要么类型报错，没有「漏了一个」的中间状态。 src/query.ts:201
三层状态process / session / turn02
按活多久分层：进程级（bootstrap/state.ts 模块单例，如 sessionId、累计成本）、会话级（AppState + 自研 store，变了要重画 UI）、轮次级（ToolUseContext，只在这次工具调用期间有意义）。分层的本质是让每个数据的可见范围刚好等于它的作用范围。
ToolUseContext轮次级上下文包02
一路传给每个工具的参数包：abortController、readFileState、appState 存取器、进度回调。放全局会导致两个并发子 agent 互相中断。

工具与执行

tool_use / tool_resultAPI 契约00
模型想调用工具时输出的结构化 JSON 叫 tool_use；客户端执行后把结果作为新消息追加回对话，叫 tool_result。硬约束：每个 tool_use 必须有配对的 tool_result，否则下一轮请求直接 400。 ensureToolResultPairing() · yieldMissingToolResultBlocks()
Tool 接口40+ 成员03
一个工具要同时回答五种消费者的问题：模型（参数格式）、权限系统（危不危险）、调度器（能否并行）、终端 UI（怎么画）、安全分类器（压成一行风险文本）。所以成员爆炸到 40+ 不是设计失误。 src/Tool.ts:362
fail-closed失败时关闭03
信息缺失时选那个「猜错了也不会出事」的方向。TOOL_DEFAULTS 里 isConcurrencySafe 和 isReadOnly 都默认 false——工具作者忘了声明，最坏结果只是慢一点，而不是数据竞争。 成立的前提是后果不对称：isDestructive 默认 false 就不是安全方向，只是统计常见值，源码把责任明确还给了作者。 src/Tool.ts:757 · TOOL_DEFAULTS
buildTool()三层展开03
所有工具的唯一构造入口，默认值因此只存在一处。展开顺序是 {...TOOL_DEFAULTS, userFacingName: () => def.name, ...def}——userFacingName 夹在中间，因为它要用 def.name，但又必须能被 def 自己的声明覆盖。 src/Tool.ts:783
五种消费者为什么是 47 个成员03
同一次工具调用被五种角色看到，每种看到的形态都不同：模型（inputSchema/description）、权限系统（isReadOnly/isDestructive）、调度器（isConcurrencySafe/interruptBehavior）、终端 UI（8 个 render*）、安全分类器（toAutoClassifierInput）。这是替代死记 47 个成员的框架。
validateInput()给模型的重试机会04
工具自己的输入合法性检查。失败不抛异常，而是返回一条给模型看的话——模型据此补参数重试。是「每个 tool_use 必须有配对 tool_result」这条硬约束的延续。单次调用 7 步链路里的 B 步。
partitionToolCalls()并发分批04
把一批 tool_use 切成若干批次：位置上相邻的安全（只读）调用合并成一批并发跑，碰到不安全的就断开另起一批。批内并发（上限 10），批与批之间严格串行。注意是「相邻」而非「所有只读的」——「读 A、改 A、再读 A」会被切成 3 批。 src/services/tools/toolOrchestration.ts
ToolSearch延迟加载工具03
工具超过 100 个时，完整 schema 能吃掉一两万 token。解法：defer_loading: true 的工具只发名字，模型要用时再通过 ToolSearch 取详情。「目录常驻，正文按需」。
结果预算tool result budget06
单个结果超 50,000 字符就落盘到 tool-results/，模型只收到 2000 字节预览 + 文件路径（包在 <persisted-output> 里）。单条消息聚合上限 200,000 字符。Read 工具显式设 Infinity 退出这套机制，否则会形成 Read→落盘→再 Read 的死循环。

上下文与预算

上下文工程context engineering06
把有限的上下文窗口当作需要主动经营的资源。三个问题：装什么、怎么装、满了怎么办。
attachment77 种注入类型06
系统需要「插一句话」给模型时（文件被外部改了、待办还剩 3 项、上下文快满了），把它伪装成用户消息，用 <system-reminder> 包起来。 src/utils/attachments.ts（3998 行）
<system-reminder>结构隔离标签06 · 14
所有系统注入内容的统一包装。系统提示词里明确告诉模型：带这个标签的内容是系统加的，与它出现的位置没有因果关系——既防止模型误以为是用户说的，也防止工具结果里的伪造标签被当成系统指令。
回灌状态写出去再读回来10
不指望模型「记住」任何东西。待办清单存在外部状态里，每轮通过 attachment 重新贴到对话末尾，永远处在「最近」的位置。代价是每轮多几百 token，换来行为的确定性。
microCompact日常清扫06
不动结构，只把很久以前那些工具结果的正文挖掉，换成 [Old tool result content cleared]。骨架还在（模型知道「我第 3 轮读过这个文件」），内容没了。
autoCompact搬家06
接近阈值（window − 13k）时触发：把整段历史交给模型写摘要，立一个压缩边界，之后只带摘要 + 边界后的新消息。有损，所以要尽量晚做——但留 13000 token 缓冲，因为写摘要本身也要花额度。
reactiveCompact救火06
请求已经发出去并被服务端以 prompt_too_long 拒绝了，就地压缩后重试同一请求。这个错误不会传给 SDK 调用方——很多调用方看到 error 字段就直接终止会话了。
memdir记忆目录07
「一个事实一个文件」：每个 .md 只存一条信息，MEMORY.md 作索引。索引常驻，正文按 turn 相关性召回。召回不用向量检索，而是让 Sonnet 读 manifest 选 ≤5 个文件——没有额外索引要维护，加一条记忆就是加一个文件。 src/memdir/findRelevantMemories.ts
Skill可插拔提示词包09
一个目录 + 一份 SKILL.md。解决的矛盾是：一个月才用一次的发布流程，写进 CLAUDE.md 就是每轮都付 token。Skill 平时只加载一行摘要（清单预算 = 上下文的 1%），模型判断该用了才注入全文。

缓存

Prompt Caching前缀缓存05
在请求某个位置打 cache_control 标记，意思是「这个位置之前的所有内容请存起来」。下次请求若开头这一大段一字节都没变，服务端直接复用，命中部分只要 10% 的价格。
前缀匹配prefix matching05
缓存匹配的是「从第一个字节开始的连续一段」，不是「内容相似」。残酷后果：越靠前的内容改动，代价越大。system prompt 里一个字符变了（哪怕 "saved 3 days ago" → "4 days ago"），后面全部作废。
缓存击穿cache break05
缓存没命中。API 只告诉你「这次重新算了」，不告诉你为什么。所以有一个 534 行的模块做事后归因：对 system 块做两份哈希（剥掉 / 保留 cache_control），分别检测内容变化与 scope/TTL 翻转。 src/services/api/promptCacheBreakDetection.ts
断点上限 4cache breakpoints05 · 06
每次请求最多 4 个 cache_control。分配：system 块末尾一个、工具清单末尾一个、消息历史里一个（会移动）。超了 API 直接 400——这就是源码里那句 Do not add any more blocks for caching or you will get a 400 的由来。
为缓存做的让步cache-driven concessions05
这个代码库里大量「乍看很怪的写法」的统一解释：冻结字符串（"saved N days ago" 在创建时算好）、只改副本（backfillObservableInput）、增量 attachment、...(cond && { key }) 而非 key: cond ? x : undefined。

权限与安全

canUseTool()10 步固定顺序12
权限判定按严格顺序走 10 个检查点，先返回的那个赢。顺序本身就是安全语义：越是「用户明确表达过的意图」和「不可挽回的破坏」越靠前，越是「图省事的全局开关」越靠后。 src/utils/permissions/permissions.ts:1158
bypass 免疫步骤 1g12 · 14
对 .git/、.claude/、.vscode/、shell 配置文件的 safetyCheck 排在 bypassPermissions 模式之前，所以它赢。用户开「全放行」的本意是「常规操作别烦我」，不是「允许你改我的 git 配置」。这是最后一道不可绕过的闸。
Plan Mode权限模式，不只是提示词10
mode: 'plan' 是 PermissionMode 的一个真实取值。这个状态下所有写工具在权限层被系统性拒绝——不是靠模型自觉，是它根本调不动。
auto 模式AI 批准 AI12
把「要不要批准」交给另一次模型调用（yoloClassifier）。但留了一批它无权决定的事：safetyCheck、requiresUserInteraction 的工具、PowerShell、Agent/REPL 工具。
Prompt Injection提示词注入14
根源是模型分不清「指令」和「数据」——对它来说都是文字。攻击者不需要接触你的机器，只需让恶意文字出现在 Claude 会读到的地方（依赖注释、GitHub issue、网页）。
五层防御没有一层声称能兜底14
① 系统提示词显式告知 ② <system-reminder> 结构隔离 ③ 输入侧净化（剥隐藏 Unicode、子进程环境变量白名单）④ 权限侧免疫（就算模型上当也执行不了——这层才是真正的闸）⑤ 对用户坦率告知。

多 Agent

子 agentsubagent11
开子 agent 最主要的动机不是并行提速，而是上下文隔离。翻几十个文件找废弃 API，主对话只需要最后那份清单——把翻文件的过程连同垃圾一起丢在子 agent 的上下文里。「用一次性上下文换一个摘要」。
fork继承式子 agent11
直接继承父级的完整对话和 system prompt。背景不用交代，前缀完全一样所以缓存直接命中，启动几乎免费。代价是回到「上下文不隔离」。 适用场景相反：探索型任务用全新上下文，接力型任务用 fork。
skipCacheWritefork 的缓存技巧05 · 11
fork 时把 cache 标记前移一位（messages.length - 2），让写入变成服务端 no-op 合并，fork 不在 KV cache 里留自己的尾巴。

三条设计原则

报告第 15 章总结的、贯穿整个代码库的三条原则。这门课的第二个目标就是把它们内化成判断力。

原则含义表现
缓存优先于优雅 只要可能击穿 prompt cache，架构就让步 冻结字符串、只改副本、增量 attachment、移动断点
默认 fail-closed 信息缺失时倒向「猜错了也不会出事」的一侧 并发安全默认 false、只读默认 false、分类器输入默认空、schema 解析失败保持 passthrough
状态写出去再读回来 不要求模型记住任何东西 待办、任务、预算、模式、技能清单全部通过 attachment 回灌
