并发分批

模型一次要你跑五个工具。哪些能同时跑，哪些必须排队？答案只有一行 if，但那一行里藏着一个几乎所有人第一眼都会看错的字：相邻。

这节课结束时你会有

  • mini-cc v2：能分批调度的执行器，跑起来你会看到两个 600ms 的调用在 608ms 内一起完成
  • 一个能自己推演的分批规则，以及它为什么不能贪心
  • 一个可以直接抄进自己项目的并发原语：带上限的生成器合流

开始之前 · Node 标准库

本课没有新增标准库，前两课的 node:fs/promises 和 node:path 继续用。

要留意的是一个 JavaScript 内建 API 的少见用法：Promise.race 配合一个会自我补充的 Set。你大概用过 Promise.race 做超时控制，本课用它做的是滑动窗口，正文第四节展开。

问题长什么样

模型一次回复里可以要求调用多个工具。比如「看看这三个文件」，它会一口气发三个 read_file。这三个读操作互不影响，同时跑显然更快。

但如果是「读 A、改 A、再读 A」呢？三个一起并行的话，第三次读可能在改完成之前就跑完，读到旧内容。

所以需要一个规则，把一批调用切成若干组，组内并发、组间排队。真实源码里这个规则写在 188 行的 toolOrchestration.ts 里，是全课程最短的关键文件，适合完整精读。

规则：合并相邻的安全调用

很多人第一眼会以为这个算法是「把所有只读的挑出来一起跑」。不对。它只合并位置上相邻的安全调用，一旦碰到不安全的就断开，后面重新起一批。

拿「读 A、改 A、再读 A」走一遍，逐行看它怎么决策：

扫描到它安全吗上一批是安全批吗动作当前批次列表
Read A是没有上一批新建批次[Read A]
Edit A否不安全的一律单独成批新建批次[Read A] [Edit A]
Read A是否，上一批是 Edit新建批次[Read A] [Edit A] [Read A]

第三行是全部关键。第三个 Read A 自己是安全的，可它前面那批是 [Edit A]，所以它跨不过去和第一批合并，只能另起一批。即使两者用的是同一个工具、读的是同一个文件。

判断条件就写在 reduce 里，只看最后一个批次：

src/services/tools/toolOrchestration.ts:109

if (isConcurrencySafe && acc[acc.length - 1]?.isConcurrencySafe) {
  acc[acc.length - 1]!.blocks.push(toolUse)          // 并入上一批
} else {
  acc.push({ isConcurrencySafe, blocks: [toolUse] }) // 另起一批
}

高亮那半边就是「相邻」的全部含义。它只回头看一格，从不翻更早的批次。

为什么不贪心一点

你可能会想，扫一遍把所有只读的收集起来一起跑，剩下的排队，并行度不是更高吗？

那样会破坏因果。「读 A、改 A、再读 A」里的第三次读，语义上就是要读改完之后的内容，模型正是这么打算的。把它提前到 Edit 之前执行，拿到的是旧内容，而且这个错误不会报错，只会让模型基于过时信息继续推理。

调度器不知道模型的意图，它唯一能依靠的信息就是模型给出的顺序。所以规则保守到只敢合并相邻项。少赚一点并行度，换的是「顺序永远不会被悄悄改写」。

再看报告里那个混合例子，能同时体现合并和断开：

模型要求：Read A · Read B · Edit C · Read D · Read E

分批结果：[Read A, Read B]   ← 相邻且都安全，合并，并行跑
          [Edit C]           ← 不安全，单独一批
          [Read D, Read E]   ← 合并，但要等 Edit C 跑完

5 个调用压成 3 批。并行度从 1 提到 2.5 倍，一个因果关系都没破坏。

另一半：批与批之间严格串行

分好批只解决了一半。另一半在 runTools()，它用一个普通的 for...of 遍历批次，每批内部 for await 消费到底才进入下一批。

[Read A, Read B]   ← 跑完，等它结束
[Edit C]           ← 才开始，跑完，等它结束
[Read D, Read E]   ← 才开始。此时 Edit 的写入已经落盘

并行只发生在批内，批与批之间永远是顺序的。因果顺序因此得到保证。

「安全」由谁说了算

判断依据是每个工具自己声明的 isConcurrencySafe(input)，也就是第 0002 课那个契约成员。注意它接收 input，因为同一个工具的安全性可以取决于具体调用。

工具声明结果
FileReadTool / GrepToolisConcurrencySafe() { return true }恒安全
BashToolreturn this.isReadOnly?.(input) ?? false按命令内容逐次判定，ls 安全，rm x 不安全
FileEditTool完全没声明吃 buildTool 的默认值 false

最后一行正是上一课 fail-closed 的真实落地。FileEditTool 的作者根本没写这个方法，系统默认它不安全。假如默认值反过来是 true，「读 A、改 A、再读 A」就会三个一起并行，产生一个只在时序不巧时才复现的数据竞争。

取值处还包了第二层保险

光有默认值不够。取值这一步本身也可能出事，所以源码在这里又兜了一道：

const isConcurrencySafe = parsedInput?.success
  ? (() => {
      try { return Boolean(tool?.isConcurrencySafe(parsedInput.data)) }
      catch { return false }   // shell-quote 解析失败等 → 保守当作不安全
    })()
  : false                     // schema 没过 → 同样不安全

两条路径都倒向 false。schema 解析失败（参数不合法，说明这次调用本来就有问题），以及 isConcurrencySafe 自己抛异常。第二条的源码注释点名了真实场景，BashTool 判断只读性时要解析 shell 引号，解析炸了就会抛。

这里的推理值得单独记住：「不知道安不安全」必须当成「不安全」，而不是当成「再想想办法猜一下」。

批内并发：为什么不用 Promise.all

批内要同时跑 N 个工具，最顺手的写法是 Promise.all。真实源码没有这么做，用的是一个叫 all() 的自研工具函数。两个理由。

一，Promise.all 等的是最终结果，中途的东西全丢了。工具执行期间要往终端实时推进度（正在读第几个文件、Bash 输出到哪一行），这些是逐个 yield 出来的事件。Promise.all 只在全部结束时给你一个数组，中间的事件没有出口。

二，Promise.all 没有并发上限。模型一次要求 50 个工具调用，全冲出去会打爆文件句柄或者触发限流。真实源码的上限是 10，可以用 CLAUDE_CODE_MAX_TOOL_USE_CONCURRENCY 覆盖。

all() 同时解决这两件事，办法是把 Promise.race 当成滑动窗口用：

src/utils/generators.ts:32 · 骨架

// 先启动一批，填满到上限为止
while (inflight.size < concurrencyCap && waiting.length > 0) {
  inflight.add(next(waiting.shift()!))
}

while (inflight.size > 0) {
  // 谁先有动静就先处理谁，不等所有人
  const { done, value, generator, promise } = await Promise.race(inflight)
  inflight.delete(promise)

  if (!done) {
    inflight.add(next(generator))   // 还没完，继续向它要下一个
    if (value !== undefined) yield value
  } else if (waiting.length > 0) {
    inflight.add(next(waiting.shift()!))  // 跑完了，腾位置给排队的
  }
}

关键在 next() 返回的对象里装着 promise 自己。race 出来之后可以精确地把这一个从 Set 里删掉，而不用去猜是哪个赢了。这个小技巧让整个池子的进出都是 O(1)。

动手：让并发变成一个可测量的数字

v2 已经建好了。它比 v1 多了三个文件（partition.ts、runTools.ts、concurrency.ts），还多了一个 sleep 工具。

cd D:\code\learning\claude-code-source\mini-cc
bun run src/v2/main.ts "并发演示"

加 sleep 是因为读本地文件太快了，一次几毫秒，并行和串行看不出差别。把时间轴拉长才能证明并发真的发生了。（真实源码里也有一个 SleepTool，用途是让模型主动等待外部状态就绪。）

剧本让模型一次发出 sleep A · sleep B · write · sleep D · sleep E，每个 sleep 600ms。你会看到：

  分批方案（共 3 批）：
  [1/3] 并发 sleep + sleep
  [2/3] 串行 write_file
  [3/3] 并发 sleep + sleep
    ⚙ sleep 等待 600ms（A）
    ⚙ sleep 等待 600ms（B）
    → 等了 600ms，标签 A
    → 等了 600ms，标签 B
  第 1 批完成，耗时 608ms
    ⚙ write_file 写入 scratch/note.md（27 字符）
    → 已写入 …
  第 2 批完成，耗时 2ms
    ⚙ sleep 等待 600ms（D）
    ⚙ sleep 等待 600ms（E）
  第 3 批完成，耗时 607ms

608ms 就是证据

两个各需 600ms 的调用，一批跑完只花了 608ms。串行的话应该是 1200ms。

同时注意第 3 批的 607ms 是在第 2 批结束之后才开始计的。整轮总耗时约 1200ms 而非 2400ms，省下的正好是被合并的那两批。

三个实验

实验 A · 验证「相邻」。打开 src/v2/model.ts，把剧本里 write_file 那一项挪到最后（放在两个 sleep D、E 后面）。重跑，分批方案会从 3 批变成 2 批，因为四个 sleep 现在连成一片了。把它挪回中间，又变回 3 批。

实验 B · 压并发上限。不改代码，直接：

MINI_CC_MAX_CONCURRENCY=1 bun run src/v2/main.ts

第 1 批的耗时会从 608ms 变成 1200ms 左右。分批方案没变，变的只是批内的实际并发度。这两件事是分开的，值得体会一下。

实验 C · 打破 fail-closed。打开 src/v2/partition.ts，把 checkSafe 里 catch { return false } 改成 catch { return true }，再让某个工具的 isConcurrencySafe 抛个异常。你会看到一个会写的工具被塞进并发批。改回来。
