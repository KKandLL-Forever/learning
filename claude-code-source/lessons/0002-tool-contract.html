工具契约

你的 Tool 有 4 个成员，src/Tool.ts 有 47 个。这一课不用背那 47 个，要弄明白的是它们为什么必须挤在同一个接口里，还有那几行 false 默认值到底挡住了什么。

这节课结束时你会有

  • mini-cc v1：带 buildTool() 和 fail-closed 默认值，外加第一个会写的工具
  • 一个能替代死记硬背的框架：「有几种消费者在看它？」
  • 一个反教条的判断：fail-closed 不等于「默认值都往保守写」，有一个成员它救不了你

开始之前 · 这一课新增的 Node 标准库

上一课的 readFile、readdir、stat、join、resolve、isAbsolute 继续用，不再重复。本课的 write_file 是第一个会写盘的工具，多带来三个函数。

来自函数做什么
node:fs/promises writeFile写整个文件。目标已存在时覆盖原内容，想追加得改用 appendFile
mkdir建目录。带 recursive: true 时把中间层一起建出来，且目录已存在也不报错，相当于 mkdir -p
node:path dirname取路径的父目录，如 dirname('a/b/c.md') 得到 'a/b'

这三个是配套用的。write_file 的 call() 里先 mkdir(dirname(full), { recursive: true }) 再写，保证目标目录一定存在，不然写一个还没建过的子目录会直接报错。

先问对问题

你在 v0 里写的 Tool 是这样的：

export type Tool = {
  name: string
  description: string
  inputSchema: JSONSchema
  call(input): Promise<string>
}

够用了。那 src/Tool.ts 凭什么膨胀到 47 个成员（其中 8 个是 render* 方法）？

「因为工具功能多」是错的答案。read_file 的功能就是读个文件，一个 call() 讲完了。

正确的问题是：同一次工具调用，有几种消费者在看它？

谁在看它需要知道什么对应成员
模型参数长什么样、这工具干嘛的inputSchema、description
权限系统这次调用危不危险、是不是只读、要不要问用户isReadOnly、isDestructive、checkPermissions
调度器能不能和别的工具并行、用户插话时该不该杀掉isConcurrencySafe、interruptBehavior
终端 UI调用时/执行中/成功/失败/被拒，各显示什么8 个 render* 方法
安全分类器把这次调用压成一行能判断风险的文本toAutoClassifierInput

五种消费者，每种看到的形态完全不同。把它们收进一个接口，回报是新增工具时编译器会逼你回答所有这些问题。漏掉「这个工具能并行吗」不会变成运行时的惊喜，要么当场报类型错误，要么退到一个保守的默认值。

顺带解释了一件 v1 里会让你意外的事

工具契约这一课改动很大，但 loop.ts 几乎没动，只多了一步 validateInput。

那 47 个成员的复杂度是给其它消费者用的，循环本身只关心 call()。每个消费者各取所需，谁也不用知道别人要什么。把它们塞进同一个接口，合理之处正在这里。

fail-closed：默认值的方向不是随手选的

47 个成员，不可能每个工具都写全。于是问题变成了另一个：作者没写时，系统该假设什么？

拿 isConcurrencySafe 举例。两个方向猜错的后果，严重程度差得很远。

默认值猜错了会怎样严重程度
true工具被安排和别的工具并行执行。两个写操作打架 → 数据损坏，而且只在时序不巧时复现难以复现的数据竞争
false它被串行执行慢一点

这就是 fail-closed（失败时关闭）：信息缺失时，选那个「猜错了也不会出事」的方向。门禁系统断电时应该锁死而不是打开，是同一个道理。

src/Tool.ts:757 · TOOL_DEFAULTS（源码原文）

const TOOL_DEFAULTS = {
  isEnabled:             () => true,
  isConcurrencySafe:     () => false,   // assume not safe
  isReadOnly:            () => false,   // assume writes
  isDestructive:         () => false,
  checkPermissions:      () => ({ behavior: 'allow', updatedInput }),
  toAutoClassifierInput: () => '',      // 跳过分类器 —— 安全敏感工具必须覆盖
  userFacingName:        () => '',
}

一个真实的案例，我替你核对过了

FileEditTool 根本没写这三个方法

src/tools/FileEditTool/FileEditTool.ts:86 用了 buildTool({...})，但通篇没有声明 isConcurrencySafe、isReadOnly、isDestructive。（我 grep 过整个文件，一处都没有。）

它靠 TOOL_DEFAULTS 兜住，被正确判定为「会写 · 须串行」。假如默认值反过来是 true，「读 A、改 A、再读 A」就会三个一起并行，产生一个只在时序不巧时才复现的数据竞争。而这一切只因为有人少写了一行。

对照另一个极端，BashTool.tsx:434 把这个问题逐次转交给了 isReadOnly：

isConcurrencySafe(input) {
  return this.isReadOnly?.(input) ?? false   // ls 安全，rm x 不安全
}

注意 isConcurrencySafe 接收 input，同一个工具的安全性可以取决于具体调用。这是接口设计里一个容易被抄错的细节。

为什么非得有 buildTool

先澄清一个容易对错号的说法。buildTool 广义上算工厂函数，可它并不是设计模式里那个「工厂模式」。工厂模式的核心是多态派发，调用方给一个类型标识，工厂决定实例化哪个具体类，返回值的真实类型对调用方是藏起来的。buildTool 一个分支都没有，你传什么它就返回什么，只把缺的字段补齐。要给它安个名字，「带默认值的规范化构造器」更贴切。

它真正挡住了什么，反过来想才看得清。假设不用它，还有两条路可走。

路一，把 47 个成员全设成必填。每写一个工具都要回答 47 个问题，没人受得了。直接出局。

路二，在接口里把它们设成可选。这条看着可行，也是真正危险的那条。成员一旦可选，默认值就跑到了每个消费者的读取处。

// 调度器里
const safe = tool.isConcurrencySafe?.(input) ?? false
// 权限系统里
const ro   = tool.isReadOnly?.(input) ?? false
// UI 里、预算裁剪器里、分类器里……

路二为什么危险

同一个默认值散落在五种消费者的几十个读取点上。只要有一个人手滑写成 ?? true，前面那个数据竞争就回来了。而这一次连 FileEditTool 的作者都是无辜的，他什么都没做错。

fail-closed 要真的生效，得有一个物理上唯一的落点。buildTool 就是这个落点。默认值只存在于 TOOL_DEFAULTS 那一处，出了这个函数，所有工具都是完整对象。源码注释把动机写得很直白：

All tool exports should go through this so that defaults live in one place and callers never need ?.() ?? default.（Tool.ts:743）

所以它的价值落在「给 fail-closed 一个唯一收口」上，跟造对象本身关系不大。

为什么必须是函数，而不是一句团队约定

如果只是补默认值，约定大家都写 { ...TOOL_DEFAULTS, ...myTool } 似乎也够用。它非得做成函数，理由在类型那一半。

src/Tool.ts:735

type BuiltTool<D> = Omit<D, DefaultableToolKeys> & {
  [K in DefaultableToolKeys]-?: K extends keyof D
    ? undefined extends D[K] ? ToolDefaults[K] : D[K]
    : ToolDefaults[K]
}

这个映射类型在类型层面镜像了运行时的展开。注意那个 -?，它把七个可默认成员全部变成必填。下游拿到的 Tool 因此没有一个可选的安全成员，也就没有理由写 ?.。类型系统直接把路二掐掉了。

源码注释里还留了条线索，说明这套写法是迁移来的：

src/Tool.ts:733

preserving arity, optional presence, and literal types
exactly as `satisfies Tool` did.

他们原先用的是 satisfies Tool。satisfies 能校验形状又保留字面量类型，可它不会帮你填默认值，消费端还是得写 ?.() ?? false。换成 buildTool 是为了拿到填充能力，而那个映射类型的活儿，就是保证换的过程里别把 satisfies 原有的类型精度弄丢。

对照：mini-cc 里真正的工厂函数

createMockModel 和 createDeepSeekModel 才是标准的工厂函数。它们封装了内部状态（turn 计数、client 实例），返回一个满足 ModelAdapter 接口的实例，调用方看不见里面。pickModel() 再进一步，根据环境变量决定造哪一个，那个才带上了工厂模式的派发味道。

buildTool 什么都没封装，输入输出都是明明白白的普通对象，是个纯变换。这个差别值得留意，因为它决定了要不要给它写测试替身：工厂函数常常需要，纯变换函数不需要。

buildTool 的展开顺序有讲究

src/Tool.ts:787

return {
  ...TOOL_DEFAULTS,
  userFacingName: () => def.name,   // ← 夹在中间
  ...def,
}

三层。userFacingName 夹在中间而没有放进 TOOL_DEFAULTS，是因为它要用到 def.name，同时又必须能被 def 自己的声明覆盖。放最后就盖不住了，放最前又拿不到 name。

但 fail-closed 有一个救不了你的成员

isDestructive 的默认 false 不是「安全方向」

前面三个默认值都能自圆其说，猜错了最多慢一点。isDestructive: () => false 是另一回事。

它说的是「大多数工具确实不具破坏性」，一个统计意义上的常见值。它并没有在保守地假设什么，所以也谈不上是安全意义上的保守值。

你写 delete_file 时忘了声明 isDestructive，没有任何东西会救你。源码注释把这层意思说得很直白，「Only set when the tool performs irreversible operations (delete, overwrite, send).」（Tool.ts:405），责任明确交还给了作者。

toAutoClassifierInput 默认返回 ''（＝跳过安全分类器）也是同一类，注释专门写了「security-relevant tools must override」。默认值在这里表示「不参与」，不表示「按最严处理」。

能带走的一条原则：fail-closed 只在后果不对称时才成立。两个方向代价差不多、或者压根没法从缺省推断的时候，正确做法是把责任显式还给作者，靠注释和 code review 兜住，别假装有个安全默认值。

动手：让默认值肉眼可见

v1 已经建好了。它比 v0 多了 buildTool.ts，多了一个会写的工具 write_file：

cd D:\code\learning\claude-code-source\mini-cc
bun run src/v1/main.ts "看看 src/v1 里有什么"

启动时会先打一张工具表：

工具清单：
  read_file  只读 · 可并发 · 可逆　上限 ∞
  list_dir   只读 · 可并发 · 可逆　上限 50000
  write_file 会写 · 须串行 · 不可逆　上限 50000

盯住 write_file 那一行

打开 src/v1/tools.ts 看它的定义。它只声明了 isDestructive: () => true，「会写」和「须串行」这两项是 TOOL_DEFAULTS 替它填的。

这正是 FileEditTool 在真实源码里的处境，只不过这里你能直接看见结果。

再看 read_file 的上限是 ∞。它显式设了 Infinity 退出结果预算机制，否则会形成「结果太大→落盘→模型再 Read 那个文件→又太大」的循环。这套机制留到第 0005 课。

两个实验

实验 A · 把默认值改反。打开 src/v1/buildTool.ts，把 isConcurrencySafe 的默认值改成 true，重跑。write_file 那行会变成「会写 · 可并发」，一个自相矛盾又危险的组合。看完改回来。

实验 B · 试试校验。v1 的循环多了 validateInput 这一步。给 write_file 传一个缺 content 的调用，它返回的是一条给模型看的话，不是异常。

Error: 参数 "content" 必须是字符串。

这是上一课那条硬约束的延续，校验失败也必须产出配对的 tool_result。与其说是错误处理，不如说是给模型的一次重试机会。模型看到这句话，自己补上参数再来一次。

下一课的伏笔

你现在有了一个会写的工具，和一套能回答「谁能并发」的契约。这两样凑齐，第 0003 课才有东西可讲：

模型一次要求：Read A · Read B · Edit C · Read D · Read E
分批结果：    [Read A, Read B]   ← 相邻且都安全 → 合并并行
              [Edit C]           ← 不安全 → 单独一批
              [Read D, Read E]   ← 合并，但要等 Edit C 跑完

5 个调用压成 3 批。注意第三批没有跨过 Edit C 去和第一批合并，即使它们用的是同一个工具。这个「不能跨」的限制看着保守，可少了它，Edit C 刚写进去的内容就可能被后面的读操作错过。
