极简内核

用 150 行写出一个和 src/query.ts 形状相同的 Agent 运行时。这一课之后，你手里会有一颗种子——后面每一课都往它身上加一个模块。

这节课结束时你会有

  • 一个能跑的 mini-cc v0（已经建好在 mini-cc/，无需 API key 也能跑）
  • 三个能解释清楚的设计决定：为什么是生成器、为什么返回终止原因、为什么状态要整体重写
  • 一条你以后每加一个模块都会用到的定位线索

你已经知道的，和这节课要改的

你在 harness-engineering 第 0002 课里写过单 Agent 循环，大概长这样：

async function run(prompt) {
  const messages = [{ role: 'user', content: prompt }]
  while (true) {
    const res = await model.complete(messages)
    if (!hasToolUse(res)) return res.text   // ← 返回答案
    messages.push(res, await runTools(res))
  }
}

这个循环是对的。Claude Code 的 query.ts 有 1680 行，但骨架跟它一模一样。这节课不改骨架，改的是骨架的三个接口——而这三处改动，正是「demo」和「能在生产里跑三小时不崩」的分界线。

改动一：返回值不是答案，是「为什么停下来」

上面那段代码 return res.text。看起来天经地义——用户问问题，函数返回答案。

但想一下调用方真正需要什么。终端 UI 拿到这个字符串之后，要判断：这是正常答完了，还是撞上轮次上限被硬停的？是用户按了 Esc，还是某个钩子拒绝让它结束？这四种情况下界面要显示的东西完全不同——但它们返回的都是一段文字。

所以 Claude Code 把这两件事拆开了：

src/query.ts:216 · query() 的签名

export async function* query(params: QueryParams): AsyncGenerator<
  StreamEvent | RequestStartEvent | Message | ...,   // ← yield 出去的：内容
  Terminal                                          // ← return 回来的：终止原因
>

答案早就通过 yield 一条条交付出去了，不需要在最后再返回一次。return 这个位置就空了出来，用于回答一个调用方真正需要的问题：控制流为什么走到了这里。

对照真实源码

query.ts 里能找到这些 return：{ reason: 'completed' }、{ reason: 'stop_hook_prevented' }（:1238）。mini-cc 的 Terminal 只有三种，但位置一样。

⚠️ 读码提醒：源码仓库的 src/query/transitions.ts 是自动生成的桩，整个文件只有 export type Terminal = any。你要从 query.ts 的实际 return 语句反推它的真实形状。src/ 下 2829 个 TS 文件里有 123 个是这种桩——读到类型莫名其妙是 any 时，先看看文件头。

改动二：为什么必须是生成器

普通函数是「调用 → 等待 → 拿到返回值」。有两件事让它不够用：

  1. 模型是逐字吐出来的。终端里文字一个个蹦出来，不是等全部生成完再显示。函数必须能「一边算一边往外交付」。
  2. 一次提问可能包含好几轮请求。模型读了三个文件才回答你，中间的每条消息、每个工具调用、每次进度更新，UI 都要实时显示。

async function* 正好解决这个：函数体里每写一个 yield x，外面的 for await 就立刻收到一个 x，函数则暂停在原地等下一次索取。

还有一个免费的好处：取消

外面调 .return()，生成器会在当前 yield 处抛出中断，finally 和 using 声明的清理逻辑自动跑。用户按 Esc 中断时走的就是这条路。

这是普通函数给不了的——普通 async 函数一旦 await 出去，你没有干净的办法让它「停在半路并清理现场」。

改动三：跨轮次的状态要显式打包

这是三处改动里最不直观的一处，也是最能体现「这段代码被真实世界打磨过」的一处。

一个跑很多轮的循环，最容易出的 bug 是某个变量在某条分支上忘了更新。query.ts 里有 9 个变量需要跨轮次携带（消息历史、压缩状态、重试计数、stopHookActive……），而循环里有 7 处 continue。

如果每处 continue 前都写 9 行赋值——漏掉一行不会报错。它只会在某个罕见路径上表现为诡异行为：比如「reactive 压缩跑了两次」或者「重试计数没归零导致死循环」。这类 bug 极难复现，因为你得先走到那条罕见分支上。

解法是把它们打包成一个 State 对象：

src/query.ts:262-276 · 源码注释原文

// 跨迭代的可变状态。循环体在每轮开头解构它，这样读取时仍是裸变量名
// （`messages`、`toolUseContext`）。各个 continue 点整体写 `state = { ... }`，
// 而不是散落 9 条独立赋值。

关键在于：整体重写意味着「要么全写，要么类型报错」。TypeScript 会拒绝一个缺字段的对象字面量。漏字段从「运行时的罕见惊喜」变成了「编译期的即时错误」——没有中间状态。

mini-cc 的 State 只有 3 个字段，看起来这个约束是小题大做。但它现在就成立，而且字段越多越值钱——这一课先把形状立对，后面几课往里加字段时你就免费拿到了这份保护。

顺带一个硬约束：tool_use 必须配对

这条不是设计选择，是 API 契约：每一个 tool_use 都必须有配对的 tool_result，否则下一轮请求直接 400。

推论有点反直觉：工具执行函数永远不能向上抛异常。工具炸了、工具不存在、参数不对——全都要转成一条 is_error: true 的 tool_result 返回，让模型自己看到错误并换个思路。

真实源码里同一约束的三个体现

  • ensureToolResultPairing() —— 请求发出前给悬空的 tool_use 补一条合成 error result
  • yieldMissingToolResultBlocks() —— 用户中断时补桩。Esc 按下的那一刻可能有三个工具跑到一半，每个都留着悬空的 tool_use
  • 整个 runOne() 被 try/catch 包住

第 3 轮读的那个文件内容，到第 30 轮还在占位置。这一个观察会引出后面四节课：结果预算（别让 800KB 日志进来）、Prompt Caching（重发的部分别重算）、三级压缩（满了怎么办）。

再做两个 30 秒的实验

实验 A —— 逼出 max_turns：把 main.ts 里的 maxTurns: 10 改成 maxTurns: 2，重跑。终止原因会从「正常结束」变成「撞上轮次上限（跑了 2 轮）」。这就是改动一的价值：调用方不需要猜。

实验 B —— 打破 State：打开 src/v0/loop.ts，在循环末尾把整体重写改成漏掉一个字段：

state = {
  messages: [...messages, assistant, { role: 'user', content: results }],
  turnCount: turnCount + 1,
  // transition: 'tool_use',   ← 注释掉这一行
}

然后跑 bunx tsc --noEmit。编译器当场拦住你。这就是「要么全写，要么类型报错」的实际手感——把它记在肌肉里，后面加到 10 个字段时你会庆幸。

接上真实模型（DeepSeek）

本课程用 DeepSeek。到 platform.deepseek.com 申请 key，然后：

# PowerShell（当前会话）
$env:DEEPSEEK_API_KEY = "sk-..."
bun run src/v0/main.ts "读一下 src/v0/loop.ts，告诉我它的终止条件是什么"

启动行会从「Mock 剧本」变成 DeepSeek (deepseek-v4-flash)。这次的工具调用是模型真的自己决定的——没有任何代码规定它该先读哪个文件。

注意刚才换 provider 时，哪些文件动了

这个项目原本调的是 Anthropic API，换成 DeepSeek 时——loop.ts、tools.ts、types.ts 一行都没改，只动了 model.ts。

这就是你在 harness-engineering 学过的「三个边界」在起作用：循环只依赖 ModelAdapter 这一个接口，不依赖任何 SDK。离线 Mock 模式能存在，也是同一个边界的副产品。

一个真实的踩坑，值得你知道

DeepSeek 同时提供两种兼容端点：https://api.deepseek.com（OpenAI 格式）和 https://api.deepseek.com/anthropic（Anthropic 格式）。

后者看起来是更好的选择——我们内部的消息结构本来就是 Anthropic 式的 content blocks（刻意跟被研究的 claude-code-source 保持一致），用它就不用写转换。但官方文档在「不支持的字段」里明确列出了 tool use。这门课整个建立在工具调用上，所以只能走 OpenAI 格式端点。

代价是 model.ts 里多了一层双向转换。两处结构性差异值得看一眼：
① 工具调用：我们放在 assistant 的 content 数组里，OpenAI 放在 tool_calls 字段上。
② 工具结果：我们塞进一条 user 消息，OpenAI 要求每个结果一条独立消息（role: 'tool'）——是一对多展开，不是一对一映射。

顺带一提，转换回来时如果模型生成的参数不是合法 JSON，model.ts 不抛异常，而是照样产出 tool_use 块、把参数留空，让后续的参数校验失败并回一条 is_error 结果。理由就是上一节那条硬约束：配对不能断。这也是你下一课要正式学的 fail-closed。
