第 0006 课 · Claude Code 源码架构

Prompt Caching

上一课反复出现的那句「前缀不能变」，理由一直没展开。这一课把缓存本身摊开：它怎么算命中，改一个字符要赔多少，以及为什么这个代码库要专门写 727 行来找是谁打穿的。

这节课结束时你会有

  • mini-cc v5：一个本地的前缀缓存模拟器，能把「命中到第几个 token」和「这一轮花了多少钱」直接打出来（--cache）
  • 一张实测的表：同样改一处，改在 system、工具区、消息中段、消息末尾，代价差着两个数量级（--break）
  • 一个会说出「是谁打穿的」的侦测器，以及它抓不到的那类情况
  • 两种 provider 设计的对照：DeepSeek 全自动，Claude 手动标断点，各自换来什么

开始之前 · Node 标准库

本课没有新的。上一课的 node:crypto 的 createHash 继续用，这次拿它给系统提示词和工具 schema 各算一个指纹，用来回答「这一轮和上一轮是不是同一份」。

一个只能看、不能碰的东西

到目前为止这门课里的每样东西都在你手上。循环是你写的，工具是你注册的，权限顺序是你排的，预算阈值是你定的。

缓存不是。它整个发生在服务端，客户端能拿到的只有账单上那两个数字：

// DeepSeek 响应的 usage 字段
{
  "prompt_cache_hit_tokens": 12416,
  "prompt_cache_miss_tokens": 7
}

但「为什么没命中」完全是客户端的事，因为前缀是客户端拼出来的。这是一个你只能观测结果、却要为原因负责的系统。本课大半篇幅都在处理这个错位。

先看清楚这两个数字值多少钱

DeepSeek V4-Flash元 / 百万 token说明
输入 · 缓存命中0.02服务端直接复用，几乎白送
输入 · 缓存未命中150 倍
输出2和缓存无关

倍数才是重点，绝对值会变（官方公告 2026 年 8 月 17 日起改成分时定价，倍数降到 30 上下）。50 倍意味着：命中率从 90% 掉到 0，这一轮的输入成本涨 10 倍不止。

这张表里有三件事

第 1 轮命中必然是 0。缓存要先写进去才谈得上命中。所以任何「第一次请求就该便宜」的期待都是错的，缓存优化的是第二次之后。

命中率不是单调上升的。第 4、5 轮掉下去了，因为那两轮的工具结果比较大，新增内容占的比例高。分母变大，命中率就被稀释。

「每轮都重发完整历史」听着浪费，账单没那么难看。第 0001 课立的那个事实到这里终于有了对价：重发的那部分几乎都是命中的，按 2% 的价钱算。

前缀是什么：从第一个字节开始比

「前缀缓存」这四个字要拆开看。它比的不是「内容相似度」，而是从第一个字节开始，连续相同到第几个字节。中间任何一处不一样，从那里往后全部作废。

而请求在 wire 上的顺序是固定的：

wire 是什么

网络协议的老词，字面是「电线」，on the wire 指数据在网线上实际传输时的那个形态，也就是序列化之后的字节。

// 内存里的样子：三个独立变量，本来没有先后
system, tools, messages

// wire 上的样子：拼成一串，顺序就此定死
`${system}${toolPart}${messagePart}`

服务端收不到你的对象，它只收到字节。所以缓存比的是后者。mini-cc 里那个 serializeRequest() 干的就是这件事。

别和第 0001 课的事件流混。那是 AsyncGenerator 逐条 yield，关心的是时序；wire 关心的是表示形态。两者正交，一份数据可以「以 wire 格式流式传输」。

┌──────────┬───────────────┬────────────────────────────┐
│  system  │     tools     │          messages          │
└──────────┴───────────────┴────────────────────────────┘
     ↑             ↑            ↑                    ↑
   改这里       改这里        改这里              改这里
   全废        后面全废      后面的废            几乎不疼

这个不对称是整节课的核心。越靠前的东西越不能动，而越靠前的东西恰好越像「配置」，看着最无害。

最后两行是同一个操作

插进去的是同一句话，字都一样。区别只有位置：一个在历史中段，一个在末尾。

中段那次多花 ¥0.0056，末尾那次多花 ¥0.0000。差了将近二十倍，而这还只是一条 12K token 的历史。真实会话动辄几十万 token，比例只会更悬殊。

这就是第 0005 课那条冻结规矩的全部理由。「已经发出去的历史别再动」不是洁癖，是这张表。

顺带解释一下为什么「什么都不改」那行的未命中不是 0。缓存以块为单位，不是逐字节，命中长度要向下取整到块边界。差一个 token 也用不上那个块。mini-cc 取 64 token 一块，DeepSeek 文档只说「以一定的 token 数量为间隔」没公布具体值，Anthropic 那边有个按模型定的最小可缓存长度（1024 或 2048 token）。

这条规矩最容易被什么绊倒

系统提示词里塞时间戳、把工具列表按 Object.keys() 的顺序拼、根据当前分支名动态改一句提示。这些改动全都落在最前面，全都看着人畜无害。

真实源码里 AgentTool 和 SkillTool 的 description 就嵌着动态生成的清单（有哪些子 agent、有哪些命令）。所以它们的 schema 会跟着环境变，而工具区排在消息前面。

谁打穿的：一个两阶段的侦探

账单只说命中掉了，不说为什么。这个代码库为此单独写了一个模块：

src/services/api/promptCacheBreakDetection.ts · 727 行

它的做法分两步，而这两步的先后是有讲究的。

阶段什么时候做什么
Phase 1请求发出之前把所有「本来不该变」的东西各记一个 hash：system、每个工具的 schema、模型名、beta 头、特性开关、effort 配置……
Phase 2响应回来之后先看命中有没有掉。掉了，才回头翻 Phase 1 记的那些指纹，找出是谁变了

为什么不能一发现 system 变了就报警

因为变了不等于打穿。变在最后、这次本来就是首次调用、或者变的那块根本没打缓存标记，都不会有损失。

先看结果再找原因，顺序反过来就是一个天天误报的告警。指纹是用来解释事实的，不是用来预测的。

判据：两个条件都要

src/services/api/promptCacheBreakDetection.ts:484 · 源码注释原文

// Detect a cache break: cache read dropped >5% from previous AND
// the absolute drop exceeds the minimum threshold.

if (cacheReadTokens >= prevCacheRead * 0.95 || tokenDrop < MIN_CACHE_MISS_TOKENS) {
  state.pendingChanges = null
  return
}

意思是：命中比上次掉了超过 5%，并且掉的绝对量超过下限（MIN_CACHE_MISS_TOKENS = 2_000），两个条件都满足才算打穿。

只看比例的话，小会话里一点抖动就报警；只看绝对量的话，大会话里掉 3% 也有好几千 token，天天报警。两个条件是在过滤两种不同的噪音。

回到 Phase 1：它到底记了些什么

Phase 1 把指纹存在一个叫 PreviousState 的类型里，20 个字段（src/services/api/promptCacheBreakDetection.ts:28）。挑几个能看出门道的：

字段为什么要盯着这个
perToolHashes每个工具的 schema 单独记一份。工具没增没减但描述变了，占了工具类打穿的 77%（源码注释里 BQ 2026-03-22 的数据）
cacheControlHash带着 cache_control 标记一起算的 hash。专门抓 scope 和 TTL 的翻转（global↔org、1h↔5m），这类变化会被普通的 systemHash 抹掉
autoModeActive
isUsingOverage
cachedMCEnabled		这三个的注释都写着不该再打穿缓存了（should NOT break cache anymore）。它们是已经修好的 bug，留在这儿是为了验证修复没有回退
cacheDeletionsPending压缩会主动删掉缓存的一部分，命中掉下去是预期内的。这个标志让侦测器闭嘴，避免把正常行为报成事故

这张字段表其实是一份事故清单。每一个字段背后都是一次真的打穿过缓存的改动。

动手二的后半段：让侦测器说话

--break 的第二部分跑了四次请求，第 3 次偷偷改一个工具的描述：

第 1 次请求                           命中        0 / 12,423  (0%)
第 2 次请求，什么都没改               命中   12,416 / 12,423  (100%)
第 3 次请求，run_tests 的描述被改了   命中      832 / 12,423  (7%)
  ⚡ 打穿了 掉 11,584 token：工具描述变了：run_tests
第 4 次请求，改回去了                 命中      832 / 12,423  (7%)

第 4 次值得多看两眼

描述改回去了，命中却还是 832，一分钱没省回来。

因为上一次写进缓存的是「改过的版本」。改回去只是又一次和上次不一样。缓存不认对错，只认和上次一不一样。

而且侦测器这一次没报警，因为它盯的是「比上次掉了」，第 4 次没再往下掉。这类侦测抓得住变坏的那一刻，抓不住一直很坏。要发现后者，得看命中率的绝对水平，那是另一套指标。

手动断点：Claude 那边多出来的一层

到这里为止讲的都是 DeepSeek 也适用的东西。接下来这一段 mini-cc 复现不了，因为DeepSeek 的缓存是全自动的：

DeepSeek 官方文档

上下文硬盘缓存技术对所有用户默认开启，用户无需修改代码即可享用。

没有断点要标，没有 scope 要选，没有 TTL 要定。你能做的只有把前缀写稳，剩下的服务端替你管。

Anthropic 那边是手动的。要缓存哪一段，得自己在请求里打标记：

src/services/api/claude.ts:359

export function getCacheControl({ scope, querySource } = {}): {
  type: 'ephemeral'
  ttl?: '1h'
  scope?: CacheScope
} {
  return {
    type: 'ephemeral',
    ...(should1hCacheTTL(querySource) && { ttl: '1h' }),
    ...(scope === 'global' && { scope }),
  }
}

三个可调的东西，各自换来一点控制力，也各自多一条打穿的路径。

一、断点数量有硬上限

src/services/api/claude.ts:3222 · 源码注释原文

// IMPORTANT: Do not add any more blocks for caching or you will get a 400

意思是：再加缓存块就会收到 400 错误。API 允许的 cache_control 块最多 4 个，这个代码库已经用满了。

所以「哪四段值得缓存」是个真正的分配问题，不是想标就标。

二、scope 决定这份缓存谁能复用

系统提示词被切成几块，每块带不同的 scope（src/utils/api.ts:321 的 splitSysPromptPrefix）：

scope谁能复用这份缓存放什么
global所有用户写死在代码里的那部分系统提示词，全世界的 Claude Code 完全一样
org同一个组织组织级的配置
null不缓存用户名、当前目录、当前时间这类会话独有的内容

切分靠一个哨兵字符串：

src/constants/prompts.ts:106 · 源码注释原文

// Boundary marker separating static (cross-org cacheable) content from dynamic content.
// Everything BEFORE this marker in the system prompt array can use scope: 'global'.
// Everything AFTER contains user/session-specific content and should not be cached.
//
// WARNING: Do not remove or reorder this marker without updating cache logic in:
// - src/utils/api.ts (splitSysPromptPrefix)
// - src/services/api/claude.ts (buildSystemPromptBlocks)

export const SYSTEM_PROMPT_DYNAMIC_BOUNDARY = '__SYSTEM_PROMPT_DYNAMIC_BOUNDARY__'

意思是：这个标记把系统提示词切成「静态、可跨组织缓存」和「动态、不该缓存」两半，标记之前的可以用 global scope，之后的是用户和会话独有的内容。末尾那句警告点名了两个必须同步改的文件。

值得注意的是这个哨兵是数组里的一个普通字符串。谁往系统提示词里插内容时插错了位置，静态区就混进了动态内容，缓存范围默默缩水，没有任何报错。又一次「位置即语义」，和第 0004 课那个十步顺序同一个母题。

三、消息级只留一个标记

src/services/api/claude.ts:3079 · 源码注释节选

// Exactly one message-level cache_control marker per request. Mycro's
// turn-to-turn eviction (page_manager/index.rs: Index::insert) frees
// local-attention KV pages at any cached prefix position NOT in
// cache_store_int_token_boundaries. With two markers the second-to-last
// position is protected and its locals survive an extra turn even though
// nothing will ever resume from there — with one marker they're freed
// immediately.

意思是：每次请求在消息区只打一个标记。打两个的话，倒数第二个位置也会被保护住，它的 KV 页会多活一轮，可是根本不会有人从那个位置续上，纯属占着推理服务的显存。

这段注释里出现了 page_manager/index.rs。一个 TypeScript CLI 的注释在引用推理服务端的 Rust 文件路径和函数名。这说明这个决定不是从 API 文档推出来的，是有人真的去读了服务端的内存回收逻辑。

TTL 那个 latch，是本课最该抄走的一招

1 小时 TTL 只对部分用户开放，资格取决于订阅状态和额度。问题是额度状态会在会话中途翻转，一翻转 TTL 就从 1h 变回默认值，而 TTL 写在 cache_control 里，属于请求内容。

内容变了就是打穿。所以源码把资格锁进进程状态，整个会话只算一次：

把资格锁在 bootstrap 状态里保持会话稳定，防止会话中途的额度翻转改变 cache_control 的 TTL，那会打穿服务端的前缀缓存，每次翻转约 2 万 token
Latch eligibility in bootstrap state for session stability — prevents mid-session overage flips from changing the cache_control TTL, which would bust the server-side prompt cache (~20K tokens per flip)（src/services/api/claude.ts:404）

一个本来正确的动态值，因为会变，所以被故意冻住了。这和第 0005 课的 seenIds 是同一个手法：凡是进入请求前缀的东西，稳定比正确重要。

两种设计，各自换来什么

DeepSeek · 自动Claude · 手动断点
要写的代码零getCacheControl、splitSysPromptPrefix、标记落位、727 行归因
能控制什么只能控制前缀写得稳不稳缓存哪几段、给谁复用、存多久
换来什么没有配置就没有配错系统提示词能跨用户复用（global）；fork 子 agent 时挪一下标记，写入就变成 no-op
代价缓存范围和时长你说了不算多出十几种打穿方式，每一种都得单独盯

这个对照能带走的东西

手动断点买到的不是「更好的缓存」，是能对缓存下判断的资格。而这份资格的价钱，就是那 727 行。

值不值取决于规模。Claude Code 的系统提示词上万 token、用户量足够大，global scope 一开，省下的是全球所有用户的第一次调用。这个量级下 727 行便宜得很。

换成你自己的 agent，多半不值。先把前缀写稳，这一条在两种 provider 下都成立，而且免费。

读一份一手资料

本课推荐（25 分钟）

首选 · src/services/api/promptCacheBreakDetection.ts:28
只读 PreviousState 那个类型，20 个字段，连注释一起大约 45 行。把它当事故清单读，每个字段问一句「什么改动会让它变」。读完你会对「哪些东西不能碰」有一份具体的名单，比任何原则都好用。

配套 · src/utils/api.ts:321 splitSysPromptPrefix()
看它怎么把系统提示词切成三到四块、每块配什么 scope。注意它有三条分支（全局缓存开、只用工具级缓存、都没有），三条分支切出来的块数和 scope 都不一样。这是「一个配置开关如何渗进请求结构」的活样本。

官方 · DeepSeek 上下文硬盘缓存
很短，五分钟。重点看它没说什么：没说块大小、没说保留时长（只说「几小时到几天」）、没说怎么主动失效。这些没说的地方就是自动方案交出去的控制力。
