第 0005 课 · Claude Code 源码架构

结果预算

权限管住了「能不能做」。做完之后的东西还得塞回对话，而一次 npm test 吐 800KB 日志。这一课看这个代码库怎么处理它，答案不是截断。

这节课结束时你会有

  • mini-cc v4：两层预算闸，都能单独跑给你看（--budget、--aggregate）
  • 一个能看出前缀稳定性的实验：同一段历史跑四轮，中途改预算，对比历史消息的内容指纹变没变（--stability）
  • 一条可以直接搬走的判断：裁剪上下文时，「删掉」和「换个地方放」是两种性质完全不同的操作

开始之前 · Node 标准库

mkdir、writeFile、join、dirname 前几课已经用过，不再重复。本课新增四样。

来自函数做什么
node:fs/promiseswriteFile 的 flag 选项第三个参数除了传编码字符串，也可以传对象。{ flag: 'wx' } 的意思是「只在文件不存在时创建」，已存在就抛错，绝不覆盖。默认的 'w' 是覆盖
node:fs/promisesrm删除文件或目录。rm(p, { recursive: true, force: true }) 相当于 rm -rf，目标不存在也不报错。演示前清场用
（错误对象本身）error.codeNode 的文件系统错误都带一个 code 字段，取值是 'EEXIST'、'ENOENT'、'ENOSPC' 这类固定字符串。判断「是哪一种失败」要看它，不要去匹配 message 里的英文
node:cryptocreateHash算摘要。createHash('sha1').update(text).digest('hex') 得到一串十六进制。这一课只拿它当指纹用，判断两次的内容是不是逐字节相同

它们在落盘那一步是连着用的：先 mkdir 建目录，再用 flag: 'wx' 写文件，写失败先看 error.code 是不是 EEXIST，是就当作「上一轮已经写过了」继续往下走，其它错误才算真失败。

一个具体的数字问题

模型没有记忆，所以每一轮都要把完整历史重新发一遍。这是第 0001 课就立住的事实，到这一课它开始收费了。

假设第 3 轮跑了个测试，日志 800KB。原样塞进 messages，会发生的事情是：

  1. 第 4 轮请求带上这 800KB
  2. 第 5 轮请求带上这 800KB
  3. 第 6 轮、第 7 轮，一直到这段历史被压缩掉为止，每轮都带

按 4 字节一个 token 粗算，800KB 大约 20 万 token。它不是花掉一次，是每轮都花一次。

直觉解法：截断

留前 2000 字，剩下的扔掉。省是省下来了，代价在于扔掉的部分从此不存在。测试日志的失败信息通常在末尾，而你刚好留了开头。

模型这时候没有任何补救办法。它想看也看不到，因为那段内容已经不在系统里的任何地方了。

这个代码库的选法：落盘

全文写到磁盘上，模型收到的换成这么一段：

<persisted-output>
Output too large (44.4KB). Full output saved to: …/.mini-cc/tool-results/call_1.txt

Preview (first 2.0KB):
> mini-cc test unit
[00001] unit · case_1 ... ok (1ms)
…
</persisted-output>

三样东西缺一不可。原始大小让模型知道自己错过了多少，路径让它能取回来，预览让它多半不用取。

这两种做法的差别

截断改变的是信息量，落盘改变的是寻址方式。

落盘之后全文一直在，只是不再占用每一轮的额度。模型缺什么自己去读，一次 read_file 的成本，换掉了每轮都付的 800KB。

而且大多数时候它不会去读。预览 2KB 通常够判断「测试过了」这种事。省下来的是「可能不需要的完整信息」，不是「信息」。

两层闸，各管各的

层管什么阈值触发时机
第一层单个结果太大工具自己声明，50,000 封顶工具刚跑完，结果进消息之前
第二层一条消息里加起来太大200,000 字符每轮请求发出之前

第一层：工具能声明，但只能往严了声明

工具契约里那个成员在第 0002 课出现过，一直没用上：

src/Tool.ts:466

maxResultSizeChars: number

关键在于它不是最终阈值。真正算阈值的函数长这样：

src/utils/toolResultStorage.ts:55

export function getPersistenceThreshold(toolName, declaredMaxResultSizeChars) {
  // Infinity = hard opt-out.
  if (!Number.isFinite(declaredMaxResultSizeChars)) {
    return declaredMaxResultSizeChars
  }
  …
  return Math.min(declaredMaxResultSizeChars, DEFAULT_MAX_RESULT_SIZE_CHARS)
}

DEFAULT_MAX_RESULT_SIZE_CHARS 是 50,000。那个 Math.min 决定了工具作者的活动范围只有一个方向：声明 20,000 会生效，声明 100,000 会被拉回 50,000。

源码里大部分工具写的是 100_000，等于什么都没说。真正调过的只有几个，BashTool 是 30_000，GrepTool 是 20_000，都是往严了调。

Infinity 那个分支为什么在 Math.min 之前

FileReadTool 声明的是 Infinity（src/tools/FileReadTool/FileReadTool.ts:342）。理由在 src/Tool.ts:462 的注释里：

persisting creates a circular Read→file→Read loop

Read 的结果落盘之后，模型要拿全文只能再 Read 一次那个文件，而那次结果又超阈值，又落盘。转不出来。

所以这个判断必须排在封顶之前。而且源码在这里加了一句额外的话：Checked before the GB override so tengu_satin_quoll can't force it back on。连运行时特性开关都不许把它扳回来。

第二层：为什么一层不够

设想 8 个 run_tests 并行，每个吐 29KB。每一个都没超 30,000 的阈值，第一层全部放行。

但这 8 个结果会一起进入同一条 user 消息。这件事第 0003 课已经埋下了：并行工具的结果收集起来，作为一条消息追加到历史里。加起来 232KB。

src/constants/toolLimits.ts:35 · 源码注释原文

// This prevents N parallel tools from each hitting the per-tool max and
// collectively producing e.g. 10 × 40K = 400K in one turn's user message.

先说清楚「替换」是什么动作

超预算之后要做的事，和第一层完全一样，只是这次由预算发起。下面统一叫替换。

被选中的那条 tool_result，它的 content 字段被换掉：

// 替换前，模型看到 29,032 字符的全文
{ type: 'tool_result', tool_use_id: 'tu_3', content: '> mini-cc test pkg_3\n[00001] …' }

// 替换后，模型看到 2,178 字符的预览。全文写进了磁盘
{ type: 'tool_result', tool_use_id: 'tu_3', content: '<persisted-output>\nOutput too large…' }

tool_use_id 没动，所以配对关系还在，API 那条硬约束不受影响。换掉的只有内容。

超了之后，怎么决定换谁

算法只有三行：

  1. 把这条消息里的结果按体积从大到小排序
  2. 依次替换，每换一个就重算总量
  3. 总量落回预算以内，立刻停手

用一组不那么整齐的数字走一遍。假设一条消息里有 5 个结果，合计 240K，预算 200K：

结果体积动作换完之后的总量
A120K替换240K − 120K = 120K，已经 ≤ 200K
B60K不动上一步就停了，根本没轮到它
C30K不动
D20K不动
E10K不动

只换了 A 一个，B 到 E 的全文模型全都看得见。

这两个选择各自在换什么

从大到小挑，是为了让替换次数最少。换一个 120K 的一步到位；从小的开始得换 E、D、C、B 四个才够，模型损失四份全文，还多写四个文件。一个 300K 的结果换掉，抵得上三十个 10K 的。

见好就收，是因为替换有代价。模型从此看不到那部分全文，可能得多跑一次 read_file。所以循环条件写的是「总量落回预算以内就停」（src/utils/toolResultStorage.ts:683），不是「全部替换」。目标是落回预算，不是把消息榨干。

真实源码在这里比 mini-cc 麻烦得多

「一条消息」在 mini-cc 里是显而易见的，一轮工具结果就是一条。真实源码里不是。

normalizeMessagesForAPI 会把连续的 user 消息合并成一条发出去，只有 assistant 消息才制造边界。所以预算的分组函数必须用同样的规则再走一遍（src/utils/toolResultStorage.ts:600）。注释里说得很直白：

The budget must group the same way or it would see N under-budget messages instead of one over-budget message and fail to enforce exactly when it matters most.

分组分错了不会报错，只会在最该生效的时候悄悄失效。这类 bug 的代价是账单，不是崩溃。

冻结：判过一次，就不再改判

到这里为止的逻辑都很直白。接下来这一段是整个模块里最反直觉的部分，也是最值钱的部分。

先补一个关于缓存的最小事实

服务端会缓存请求的开头。下次请求如果开头这一大段和上次一字节都不差，这部分直接复用，只收 10% 的钱。

关键在于它比的是从第一个字节开始的连续相同。中间任何一处变了，从那里往后全部作废，得重新算一遍全价。

所以「历史消息」有一个平时想不到的性质：它一旦发出去，就最好再也别动了。动一个字符，后面几十轮攒下的缓存全废。

问题就出在这里

预算每一轮都要跑，而每一轮发的都是完整历史。同一条老消息会被反复判断。

接着上面那个例子往下走。第 3 轮那条消息有 A(120K) B(60K) C(30K) D(20K) E(10K)，预算 200K，当时换掉了 A：

轮次发生了什么预算对第 3 轮那条消息做了什么
第 3 轮消息第一次出现，240K 超预算判断一次，换掉 A，把 A 的替换文本记下来
第 4 轮同一条消息又被发一遍不重新判断，查表把 A 的那串字原样贴回去
第 5 轮有人把预算调到 60K按新预算 B 也该换了。但 B 见过，不动

第 5 轮那一格是整件事的要害。明明「该换」，却不能换。

因为 B 的全文在第 3 轮和第 4 轮已经发出去两次了。这一轮突然换成预览，请求前缀就从 B 那个位置断开，B 后面所有内容的缓存一起作废。省下 60K，赔掉几十万 token 的缓存命中。

换个说法

把已经发出去的历史想成寄出去的信。收件人手里有一份副本，你手里有一份底稿。只要两份对得上，续写下一页就行。

现在你觉得第 3 页写得太啰嗦，想删掉一半。可以删，但代价是收件人手里那份对不上了，整封信得重寄。

省纸和重寄，哪个划算，取决于信有多长。在一个跑了几十轮的会话里，答案永远是别动。

所以这个模块用两个字段把决定钉死：

src/utils/toolResultStorage.ts:390

export type ContentReplacementState = {
  seenIds: Set<string>              // 过过一遍预算检查的，无论替没替
  replacements: Map<string, string> // 其中被替换的，连当时给模型看的那串字一起存
}

规则只有一句：进了 seenIds，这个结果就不再改判。

分类上一轮的决定这一轮怎么处理
mustReapply替换过原样再贴一次。纯 Map 查表，零 IO，逐字节相同，不可能失败
frozen见过，没替从此不许再替。就算现在超预算了也不替
fresh没见过这一轮唯一能动的

对照上面那个例子，第 5 轮的时候：A 是 mustReapply（查表贴回），B 到 E 是 frozen（碰都不碰），第 5 轮新产生的那些结果才是 fresh。

所以预算模块随着会话变长，做的事越来越少。老消息全是查表，真正需要判断的永远只有最新那一条。

还有一个细节值得注意：replacements 存的是字符串本身，不是「稍后重新生成」。源码解释了为什么：

src/utils/toolResultStorage.ts:474 · 源码注释原文

// `replacement` is the exact string the model saw — stored rather than
// derived on resume so code changes to the preview template, size formatting,
// or path layout can't silently break prompt cache.

改一下预览模板、改一下体积的显示格式，重新生成出来的字符串就和当初发出去的差一点点。差一个字符，前缀就断了。存下来是唯一可靠的做法。

读这张表

盯 hash 那一列。它是第一条 user 消息里所有 tool_result 内容拼起来的指纹。

带状态：预算怎么改，那条历史消息一个字节都没动。因为老决定走的是「查表贴回去」，根本没重新判断。

不带状态：预算一改，同一条历史消息重新算了一遍，这次它超了 60,000，于是多替了 4 个。hash 变了，那一处往后的缓存全废。

「新替 / 查表贴回」这两个数字也值得看。带状态那边从第 2 轮起就是 0 / 2，说明预算模块每轮做的事情越来越少，只是把老账贴回去。

一个补丁，讲的是别的事

第一层那个函数开头有个分支，和体积毫无关系：

src/utils/toolResultStorage.ts:280 · 源码注释节选

// inc-4586: Empty tool_result content at the prompt tail causes some models
// to emit the \n\nHuman: stop sequence and end their turn with zero output.
// … Several tools can legitimately produce empty output (silent-success
// shell commands, MCP servers returning content:[], REPL statements, etc.).
// Inject a short marker so the model always has something to react to.

if (isToolResultContentEmpty(content)) {
  return { ...toolResultBlock, content: `(${toolName} completed with no output)` }
}

inc-4586 是个事故编号。空的工具结果落在提示词末尾时，某些模型会把 </function_results> 后面那两个换行误当成轮次边界，直接收工，一个字都不输出。

而空输出完全合法。一条静默成功的 shell 命令就是这样。

所以补丁是塞一句废话进去，让模型总有东西可以反应。这一行代码解释不了自己，删掉它测试全绿，几个月后又会有人删掉它。那段注释就是它的全部生命保障。

留给你的一个漏洞

看第 2 轮那次 read_file。它读回来的是完整的 44.4KB，而 read_file 声明了 Infinity，第一层放它过去，第二层也豁免它。这 44.4KB 就这么原样进了历史，一轮没少。

所以豁免不是免费的。真实源码里 Read 是有边界的，它自己带行数上限和 maxTokens，源码注释写的是 the tool already self-bounds via its own limits。mini-cc 的 read_file 什么边界都没有。

给 read_file 加上 offset 和 limit 参数，让模型能只取自己要的那几行。这是本课的练习，也是豁免必须配自限这条规矩的现场演示。
