速查：本项目中的设计模式与范式

本项目的代码不是随手堆出来的——它刻意用了一批经典的设计模式和编程范式。这一页把每一个都单独拎出来讲清楚：它是什么、代码里在哪、为什么这么写、不这么写会怎样。看懂这些，你就能把同样的套路搬到自己的 Harness 里。

第 1～8 条来自第 0002 课（单 Agent 循环）；第 9～11 条来自第 0003 课（多 Agent 系统）。

设计模式不是"炫技"。每一个模式都在解决一个具体的"如果以后要改，怎么才能只改一处"的问题。学模式的正确姿势是记住它解决的痛点，而不是背它的 UML 图。

全景图：三个边界背后的模式

1. 适配器模式（Adapter）

在哪：model.ts —— ModelAdapter 接口，加上 MockModel 和 DeepSeekModel 两个实现。

解决什么：不同 LLM 厂商的 API 长得不一样（DeepSeek/OpenAI 的 SSE、本地模型的裸输出……）。适配器把这些"外部形状各异"的接口，统一"翻译"成 Agent Loop 认识的一种形状：stream(messages, tools) → AsyncIterable<ModelResponseChunk>。

export interface ModelAdapter {
  stream(messages: Message[], tools: ToolDefinition[]): AsyncIterable<ModelResponseChunk>;
}

// 适配器 A：假的，不需要 API Key，用于教学 / 测试
export class MockModel implements ModelAdapter { /* ... */ }

// 适配器 B：真的 DeepSeek API（OpenAI 兼容），把它的流式分片翻译成统一的 chunk
export class DeepSeekModel implements ModelAdapter {
  async *stream(messages, tools) {
    const stream = await this.client.chat.completions.create({ stream: true, /* ... */ });
    for await (const part of stream) {
      const delta = part.choices[0]?.delta;
      if (delta?.content) {
        yield { type: "text", text: delta.content };   // ← 翻译动作
      }
      // ... 工具调用分片按 index 累积后再 yield tool_use
    }
  }
}
识别适配器的方法：看到"一个接口 + 多个 implements，每个实现把某种外部 API 包一层"，那就是适配器。它的价值是让核心逻辑对『用哪家模型』一无所知。

2. 策略模式（Strategy）

在哪：main.ts —— 把哪一个 ModelAdapter 传进 Agent，就是在"选择策略"。

与适配器的区别：适配器关注"怎么把外部接口包成统一形状"，策略关注"运行时选哪一个实现"。同一份代码，两种视角。换模型只需要改一行注入：

// 学习阶段用 Mock，一行都不用改 Agent
const agent = new Agent({ model: new MockModel() }, tools);

// 想调真 DeepSeek？只换这一行策略：
const agent = new Agent({ model: new DeepSeekModel(process.env.DEEPSEEK_API_KEY!) }, tools);

Agent 内部完全不知道自己拿到的是 Mock 还是真模型——它只调 this.config.model.stream(...)。这就是面向接口编程（program to an interface, not an implementation）的直接收益。

3. 注册表模式（Registry）

在哪：tools.ts —— ToolRegistry 用一个 Map 管理所有工具。

解决什么：工具是"可插拔"的。你不希望 Agent Loop 里写死 if (name === "get_weather")。注册表提供三个动作：注册、按名字查、执行，让工具集合可以随时增删而不动核心循环。

export class ToolRegistry {
  private tools = new Map<string, Tool>();

  register(tool: Tool): this { /* 注册 */ }
  getAllDefinitions(): ToolDefinition[] { /* 给模型看的清单 */ }
  async execute(name: string, input): Promise<string> { /* 按名字执行 */ }
}

4. 链式调用 / 流式接口（Fluent Interface）

在哪：ToolRegistry.register 的返回值是 this。

细节：方法结尾 return this，就能把多次调用串成一条链，读起来像在"声明"而不是"一步步操作"：

register(tool: Tool): this {
  this.tools.set(tool.definition.name, tool);
  return this;                 // ← 关键：返回自身，才能链下去
}

// main.ts 里的效果：
const tools = new ToolRegistry()
  .register(getWeatherTool)
  .register(calcTool);

5. 依赖注入 / 控制反转（DI / IoC）

在哪：agent.ts 的构造函数。

解决什么：Agent 自己不 new 任何依赖——model 和 tools 都是从外面"注入"进来的。谁来组装？main.ts（组合根 composition root）。好处：测试时可以塞一个假 model，生产时塞真 model，Agent 一个字都不用改。

export class Agent {
  constructor(
    private config: AgentConfig,   // 里面装着 model 这个依赖
    private tools: ToolRegistry,    // 工具依赖也从外面来
  ) {}
}
控制反转的"反转"指的是：创建依赖的控制权，从对象自己手里，反转到了外部调用者手里。这就是为什么第 2、3、5 条能配合得这么顺——正因为依赖是注入的，你才能自由地"选策略"。

6. 迭代器 / 异步生成器（Iterator via async generator）

在哪：async *stream(...) 和 async *run(...) 里的 yield。

解决什么：流式输出要求"边生成边吐"，而不是"全部算完再一次性返回"。异步生成器（async * + yield）让你用最朴素的 for await ... of 就能一块一块地消费，既做到了流式，又保留了普通函数的可读性。

async *run(userInput: string) {
  for (let turn = 0; turn < maxTurns; turn++) {
    for await (const chunk of this.config.model.stream(messages, defs)) {
      yield chunk;              // ← 每来一块就吐给上层，不用等整轮结束
    }
  }
  yield { type: "done", result };
}

// main.ts 消费端，天然的流式：
for await (const chunk of agent.run(userInput)) {
  if (chunk.type === "text") process.stdout.write(chunk.text ?? "");
}

7. 标签联合类型（Tagged / Discriminated Union）

在哪：types.ts 的 ModelResponseChunk（靠 type 字段区分）和 ContentBlock。

解决什么：循环里流动的数据有好几种形态——文本、工具调用、结束信号。用一个带 type 标签的联合类型，TypeScript 就能在 if (chunk.type === "tool_use") 之后自动收窄类型，让你安全地访问 chunk.toolUse。这是把"运行时的分支判断"和"编译期的类型安全"绑在一起的经典手法。

export type ContentBlock =
  | { type: "text"; text: string }
  | { type: "tool_result"; tool_use_id: string; content: string };
//        ↑ 共同的 "type" 字段就是"标签"，用来区分是哪一种

8. 错误隔离 / 优雅降级（Error Isolation）

在哪：ToolRegistry.execute 里的 try/catch。

解决什么：工具执行失败时，不要抛异常终止整个循环，而是把错误信息当成 tool_result 返回给模型，让模型自己决定重试还是向用户解释。这是 Harness 韧性（resilience）的核心设计——把"失败"变成"模型能读懂的一条普通结果"。

async execute(name: string, input): Promise<string> {
  try {
    return await tool.execute(input);
  } catch (err) {
    const message = err instanceof Error ? err.message : String(err);
    return `工具执行失败：${message}`;   // ← 把异常"降级"成一条结果，循环继续
  }
}

以下三条来自第 0003 课的多 Agent 系统。

9. 中介者模式（Mediator）

在哪：orchestrator.ts —— Orchestrator。

解决什么：多个 Worker 之间不直接互相调用，所有沟通都经过 Orchestrator 转发。这样每个 Worker 只需要认识"编排者"一个对象，而不需要知道其他 Worker 的存在。如果让 Worker 彼此直接引用，N 个 Worker 就会织成一张 N×N 的关系网，加一个删一个都牵一发动全身；有了中介者，关系网被压成一颗星形。

async run(userTask: string) {
  const chosen = await this.router.route(userTask, this.workers);
  const results: AgentMessage[] = [];
  for (const name of chosen) {
    const worker = this.workers.find((w) => w.name === name);
    // ← Worker 之间从不直接对话，全部经 Orchestrator 中转
    const result = await worker!.run(userTask);
    results.push({ from: name, to: "orchestrator", content: result });
  }
  return { answer: this.synthesize(results), log };
}
识别中介者：看到"一堆对象都只跟中间那一个说话，彼此之间不直接引用"，那就是中介者。它把"多对多"的耦合收敛成"多对一"。

10. 工厂函数（Factory Function）

在哪：worker.ts —— makeWorker(opts)。

解决什么：创建一个 Worker 要经过好几步——new 一个 Agent、塞进 model 和 system prompt、把它的流式 run 收敛成一个 Promise。工厂函数把这套装配藏在一个函数背后，调用方只管传"我想要什么"（配置），拿回一个现成的 Worker，不必关心里面怎么拼的。

// 调用方极其干净——不用 new Agent、不用管流式细节
const weatherWorker = makeWorker({
  name: "weather",
  description: "回答天气相关问题",
  systemPrompt: "你是天气助手，只回答天气问题。",
  model: new ScriptedModel("北京今天晴，25°C，湿度 45%。"),
});

它和第 5 条"依赖注入"是搭档：工厂负责组装，注入负责把依赖（model、tools）从外面递进来。

11. 外观模式（Facade）

在哪：worker.ts 里 Worker.run 的实现。

解决什么：第 0002 课的 Agent.run 是个异步生成器——要用 for await 一块块消费、还要自己判断 chunk.type === "done"。但 Orchestrator 并不关心这些流式细节，它只想要"给个任务、还我一个字符串"。外观模式就是用一个简单接口，罩住背后那套复杂调用。

async run(task: string): Promise<string> {   // ← 对外只是"任务进，字符串出"
  let final = "";
  for await (const chunk of agent.run(task)) {   // ← 复杂的流式循环被藏在里面
    if (chunk.type === "done" && chunk.result) final = chunk.result.response;
  }
  return final;
}
外观 vs 适配器：两者都"包一层"，但目的不同。适配器是为了兼容（把 A 形状转成 B 形状）；外观是为了简化（把复杂的多步调用收成一个易用入口）。这里 Worker.run 把"流式生成器"简化成"一个 Promise"，是典型的外观。
把 9～11 连起来看，就是编排者–工作者（Orchestrator-Workers）这个智能体协作架构的三块拼图：中介者定义"谁跟谁说话"，工厂负责"批量造出工作者"，外观让"工作者用起来足够简单"。

一张表记住它们

模式 / 范式 代码位置 解决的痛点
适配器 model.ts 不同厂商 API 形状不一，统一成一种
策略 main.ts 注入 运行时换模型，核心不改
注册表 tools.ts 工具可插拔，不写死 if 分支
链式调用 register(): this 声明式地组装工具集
依赖注入 / IoC agent.ts 构造函数 依赖从外面来，可测试、可替换
迭代器 / 异步生成器 async * + yield 流式输出，又保持可读
标签联合类型 types.ts 分支判断 + 编译期类型安全
错误隔离 ToolRegistry.execute 工具失败不中断循环，交给模型处理
中介者 orchestrator.ts Worker 只跟编排者说话，把多对多耦合收成星形
工厂函数 makeWorker() 把 Worker 的装配藏在函数背后，调用方只传配置
外观 Worker.run 用"任务进、字符串出"罩住背后的流式循环
一个彩蛋：这些模式能配合得这么顺，根源都是同一条原则——面向接口编程，而非面向实现。ModelAdapter 和 Tool 两个接口是整套设计的"缝合线"，正因为核心循环只依赖接口，适配器、策略、注册表、依赖注入才能各就各位。
