第 0003 课：多 Agent 系统

前两课我们打磨了一个 Agent 循环。这一课进入 Level 2：把一个 Agent 拆成多个，各自专精，由一个"编排者"统一调度。这就是生产级 Harness（如 Claude Code 的 subagent、各类 Agent 框架）的骨架。

多 Agent 不是"多个模型堆在一起"。它真正解决三件事：上下文隔离（每个 Agent 只看自己该看的）、专精分工（不同 system prompt / 工具集）、可并行（互相独立的子任务同时跑）。

为什么需要多 Agent？

当你把所有能力塞进一个 Agent，会遇到三堵墙：

  • 上下文膨胀——工具越多、历史越长，模型越容易"分心"、越贵、越慢。
  • 职责混乱——一个 system prompt 想同时当天气专家、数学家、文字编辑，哪个都做不精。
  • 无法并行——单循环只能一步步来，独立子任务白白排队等待。

把它们拆成多个专精 Worker，再加一个 Orchestrator 统一调度，三堵墙就都拆掉了。

核心架构：Orchestrator–Workers

整个系统就四步：路由 → 分发 → 收集 → 汇总。我们把每一步都拆成一个小模块，逐个实现。

第一步：消息传递协议

多个 Agent 之间靠"消息"沟通。先定义最小的消息结构——谁发给谁、内容是什么。有了统一的 AgentMessage，整条协作链路就能被记录、回放、调试。

// src/0003-multi-agent/types.ts
export interface AgentMessage {
  from: string;
  to: string;
  content: string;
}

// Worker：能接收任务、返回结果的子 Agent
export interface Worker {
  name: string;
  description: string; // 给 Orchestrator 看，用于路由决策
  run(task: string): Promise<string>;
}

// Router：决定把任务交给哪些 Worker
export interface Router {
  route(task: string, workers: Worker[]): Promise<string[]>;
}

第二步：把 Agent 包成 Worker（上下文隔离）

关键设计：每个 Worker 内部持有一个独立的第 0002 课 Agent 实例。独立的 Agent 意味着独立的 messages 历史——这就是"上下文隔离"，一个 Worker 的对话永远不会污染另一个。

// src/0003-multi-agent/worker.ts
export function makeWorker(opts: {
  name: string;
  description: string;
  model: ModelAdapter;
  systemPrompt: string;
  tools?: ToolRegistry;
}): Worker {
  // ← 直接复用第 0002 课的 Agent，一行没改
  const agent = new Agent(
    { model: opts.model, systemPrompt: opts.systemPrompt },
    opts.tools ?? new ToolRegistry(),
  );

  return {
    name: opts.name,
    description: opts.description,
    async run(task: string): Promise<string> {
      let final = "";
      for await (const chunk of agent.run(task)) {
        if (chunk.type === "done" && chunk.result) final = chunk.result.response;
      }
      return final;
    },
  };
}
注意这里 0002 课的 Agent 一个字都没改就被复用了。这正是前两课"三个边界"设计的回报——因为 Agent 只依赖 ModelAdapter 接口，它天然可以被嵌进更大的系统。

第三步：路由器（决定交给谁）

Orchestrator 怎么知道该把任务给哪个 Worker？这就是 Router 的活。最容易理解的是关键词路由——规则驱动、离线可用：

// src/0003-multi-agent/router.ts
export class KeywordRouter implements Router {
  constructor(private rules: { keywords: string[]; worker: string }[]) {}

  async route(task: string, workers: Worker[]): Promise<string[]> {
    const chosen = new Set<string>();
    for (const rule of this.rules) {
      if (rule.keywords.some((k) => task.includes(k))) chosen.add(rule.worker);
    }
    // 兜底：没命中就交给第一个 Worker
    if (chosen.size === 0 && workers.length > 0) chosen.add(workers[0].name);
    return [...chosen];
  }
}

生产环境里通常换成模型路由（ModelRouter）：把每个 Worker 的 description 拼进 prompt，让 LLM 自己判断该调用哪个 Worker。接口 Router 不变，换实现即可——又是策略模式。

第四步：编排者（路由 · 分发 · 收集 · 汇总）

// src/0003-multi-agent/orchestrator.ts
export class Orchestrator {
  constructor(private workers: Worker[], private router: Router) {}

  async run(userTask: string) {
    const log: AgentMessage[] = [];
    log.push({ from: "user", to: "orchestrator", content: userTask });

    // 1. 路由
    const chosen = await this.router.route(userTask, this.workers);

    // 2. 分发 + 收集（顺序执行；独立任务可用 Promise.all 并行）
    const results: AgentMessage[] = [];
    for (const name of chosen) {
      const worker = this.workers.find((w) => w.name === name);
      if (!worker) continue;
      log.push({ from: "orchestrator", to: name, content: userTask });
      const result = await worker.run(userTask);
      const msg = { from: name, to: "orchestrator", content: result };
      results.push(msg); log.push(msg);
    }

    // 3. 汇总
    const answer = this.synthesize(results);
    log.push({ from: "orchestrator", to: "user", content: answer });
    return { answer, log };
  }
}
第 2 步的 for 循环是顺序执行，仅为教学清晰。真实系统里，相互独立的子任务应该用 Promise.all(chosen.map(...)) 并行跑——这是多 Agent 相比单循环的一大性能优势。

第五步：运行它

示例里我们用 ScriptedModel（返回固定回复的假模型，实现了 ModelAdapter），所以无需 API Key就能跑：

npm run lesson-0003

任务 "北京今天天气怎么样？顺便算一下 2 + 3 × 4" 会同时命中 weather 和 math 两个 Worker，输出：

用户任务： 北京今天天气怎么样？顺便算一下 2 + 3 × 4

=== 消息流（Message Passing）===
user → orchestrator：北京今天天气怎么样？顺便算一下 2 + 3 × 4
orchestrator → weather：北京今天天气怎么样？顺便算一下 2 + 3 × 4
weather → orchestrator：北京今天晴，25°C，湿度 45%。
orchestrator → math：北京今天天气怎么样？顺便算一下 2 + 3 × 4
math → orchestrator：2 + 3 × 4 = 14。
orchestrator → user：【weather】北京今天晴，25°C，湿度 45%。
【math】2 + 3 × 4 = 14。

=== 最终答案 ===
【weather】北京今天晴，25°C，湿度 45%。
【math】2 + 3 × 4 = 14。

那条消息流就是多 Agent 系统最宝贵的可观测性——每一次路由、分发、回传都被记录下来，出问题时一眼就能定位是哪个环节。想接真实模型？把 ScriptedModel 换成第 0002 课的 DeepSeekModel（记得配 .env + dotenv）即可。

小测验

第 1 题

多 Agent 系统相比单 Agent 的核心优势是什么？

让底层模型的参数量变得更大
上下文隔离 + 专精分工 + 可并行
完全不再需要任何 API Key
自动消除模型的所有幻觉

第 2 题

以下哪一项不是 Orchestrator 的职责？

路由：决定任务交给哪个 Worker
收集各 Worker 的结果并汇总成最终答案
亲自训练每个 Worker 使用的底层模型
在 user 和 Worker 之间传递消息
